## Deviations candidates

- `WerkaStore._pendingBreakdownItems` groups records with an empty supplier reference by trimmed supplier name, but `_pendingDetailItems` filters only by reference. Selecting one blank-reference group can therefore show all blank-reference records. Kept as V2 behavior; do not change without direction.
- `WerkaArchiveSentHubScreen._loadCurrent` starts daily, monthly and yearly loads concurrently, but each independently clears the shared loading flag in `finally`. One response can therefore end the loading state while the other requests are still pending. This inherited behavior is documented, not changed or represented as a completed controller.
- `WerkaArchiveListScreen._lastDayOfMonth` subtracts a fixed 24-hour duration from local midnight on the first of the next month. On a midnight DST change it can produce a non-midnight value or the preceding calendar date; the source-derived model preserves this behavior rather than replacing it with a calendar-day subtraction. - The unwired daily, monthly/yearly, sent-hub and list archive flows reject superseded page/refresh results and their loading completions. V2's corresponding load methods check only `mounted` and can publish an older overlapping response; the stricter flows are an intentional safety difference, not a claim that an already-sent read was canceled. The sent flow still retains V2's single shared flag, so a current panel can clear it while other panels remain pending.
- The unwired batch lookup flow will not start the second customer read after account invalidation or disposal, while V2's `_resolveItem` does not check `mounted` between its two awaits. This is an intentional safety difference and does not cancel the first read or make the real catalog adapters safe.
- With integrator direction, the new Werka store rejects late reads, bootstrap values and mutation-result projections from a replaced session or changed read scope; it also consults the actual active session by default on each snapshot read. It cannot itself force a rendered view to reread when auth changes, so integration still needs a tested notification/remount. New Werka mutations recheck the same identity, scope and permission immediately before every send. The unwired receive flow additionally keeps an instance-local uncertain-write lock after a failed send, including after refresh; this intentional safety difference is not cross-remount reconciliation. V2's singleton and write calls do not add these checks. This is an intentional safety difference; it does not cancel a server mutation or authorize an automatic retry after an uncertain result. A caller must retain the generation from before the write and treat an old or uncertain result as such. This is not a redirect-hop guard, request cancellation or a complete auth lifecycle solution.
