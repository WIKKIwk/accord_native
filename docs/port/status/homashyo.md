## Deviations candidates
- V2 releases its Home lock after a pending-key read fails. This checkpoint intentionally fails closed and adds localized status-only retry/hold feedback. Stock/issue saves, their retries, printer selection and all reprints are temporarily unavailable until durable acknowledgment and same-scope exclusion are established. There is no claim of cross-process transactional storage, server idempotency or native timing.

## Scanner limitations and evidence
- V2 `mobile_scanner` checks Android barcode corner points against the whole centered scan window and uses iOS Vision region of interest; it supports tap-to-focus and ML Kit auto-zoom. The Expo scanner reads the entire preview and omits those actions. The branch requires the operator to confirm the detected code before source lookup; this is an explicit V2 deviation and does not establish ROI parity.
- Expo SDK 58's [Camera documentation](https://docs.expo.dev/versions/v58.0.0/sdk/camera/) says bounds can be empty or incomplete. Installed Android transforms barcode corners into view coordinates; the iOS metadata and alternate detection paths require real-device coordinate verification. Expo exposes a numeric zoom prop and autofocus mode, but no scan-window/region, touch-focus point, or equivalent ML Kit auto-zoom API established by this audit. The installed CameraView suppresses identical detections for 500 ms, another behaviour to compare. No new native bridge is assumed. React layout-effect timing is only mock-tested; it does not prove native events or camera release timing on a device.
- The isolated V2 scan-window geometry tests passing 28/28 demonstrate V2 math only, not parity of camera crop, coordinates, focus or zoom on Expo. Camera behavior and a possible closer ROI solution remain open for the user’s iOS and Android device checks.
