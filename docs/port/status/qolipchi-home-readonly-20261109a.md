## Safety blockers reproduced against exact main

1. `authorizedFetch.ts:27-55` checks `beforeSend` once per initial or 401-retry send, but not between redirect hops. A mock same-origin 302 arriving after witness invalidation causes a second `fetch` with the old bearer token. The role rejects the eventual result, but that is too late to prevent the second send. The mock-only regression reproduces this with no real network or credentials.
2. A mock 401 arriving after a login transition starts still enters `refreshSession`: `activeSessionToken` remains available while the old session object is active. The shared refresh can invoke credential authentication before the role sees and rejects the stale result.
3. Even if refresh starts while the witness is valid, a logout can begin during account lookup without changing the auth epoch yet. When lookup finishes, the existing epoch-only check can still invoke credential authentication after the witness is invalid. A mock-only test reproduces this actual shared-auth call sequence.

The existing image transport uses the same redirect loop without a guard; the catalog wrappers also use `authorizedFetch`. Caller `RequestInit.redirect` is overwritten, and an abort signal does not introduce a synchronous witness check at each hop. Raw `fetch` is not a supported replacement for the existing authentication, timeout, refresh and credential-stripping rules. No safe existing transport route was identified.

## Proposed opt-in integration fix, not yet implemented at this checkpoint

A separately reviewed, explicit opt-in could add a synchronous, non-revivable guard without changing legacy/default callers: check it after request arguments are constructed and immediately before every initial, redirected and 401-retry `fetch`; reject non-boolean, asynchronous, throwing, reentrant or revoked checks. Recheck after the first response and before entering refresh. The original witness must also be checked across the asynchronous account lookup and immediately before the actual reauthentication `fetch` inside `authenticateAccount`, including after its dynamic import. Guard failures must not be swallowed by legacy refresh catch/disconnect handling, and stale guarded readers must not publish or retry after joining an unguarded refresh. Existing refresh coalescing needs explicit tests in both guarded/unguarded orders and across distinct witness lifetimes so the new guarded caller neither cancels nor changes a legacy caller's result. Legacy-only same-origin redirect credential retention, cross-origin stripping, redirect limit, mutation behavior, timeouts, 401 single-flight, ordinary login arguments, and image behavior must remain as before. The pending login 307/308 redirect decision and notifications are separate and must not be changed here.

No JavaScript guard makes a native dispatch atomic with later session invalidation, cancels an already-dispatched request, or resolves an ambiguous write. An account-store operation already entered before invalidation may also have its own asynchronous effects. Independent review must decide these boundaries and the separately held login-redirect issue before a production route is considered.
