The candidate only starts the initial blocks GET, reads the saved block order, starts each block's locations GET, supports the real 160 ms source search and tab selection, and displays native read-only grids. ## Safety races reproduced on the unmodified main baseline

1. `authorizedFetch.ts:27-55` checks `beforeSend` once per initial or 401-retry send, but not between redirect hops. A mock same-origin 302 arriving after witness invalidation causes a second `fetch` with the old bearer token. The role rejects the eventual result, but that is too late to prevent the second send. The mock-only regression reproduces this with no real network or credentials.
2. A mock 401 arriving after a login transition starts still enters `refreshSession`: `activeSessionToken` remains available while the old session object is active. The shared refresh can invoke credential authentication before the role sees and rejects the stale result.
3. Even if refresh starts while the witness is valid, a logout can begin during account lookup without changing the auth epoch yet. When lookup finishes, the existing epoch-only check can still invoke credential authentication after the witness is invalid. A mock-only test reproduces this actual shared-auth call sequence.

Before the opt-in checkpoint, the existing image transport used the same redirect loop without a guard; it still does for legacy image calls, and the catalog wrappers also use `authorizedFetch`. Caller `RequestInit.redirect` is overwritten, and an abort signal does not introduce a synchronous witness check at each hop. Raw `fetch` is not a supported replacement for the existing authentication, timeout, refresh and credential-stripping rules. No safe existing transport route was identified.

## Conservative transport guard and explicit recovery gap

The separately committed opt-in guard checks the captured original witness before every initial, redirected and 401-retry GET and after asynchronous waits. It pins GET/HEAD on the actual request, closes timed-out gates, rejects invalid/asynchronous/reentrant checks, and preserves the original unguarded fetch expression. It cannot recall or make atomic an already-dispatched native request. `authorizedImageFetch`, ordinary login/logout, notifications and the separately unanswered login 307/308 redirect policy are unchanged. See `qolipchi-guard-readonly-20261109a.md` for its independent review, exact coalescing and default-behavior tests.

A guarded 401 only observes an independently running legacy refresh of the same session/epoch or uses an already-rotated token. It never initiates credential authentication, saved-account publication or session writes. If no independent refresh succeeds it raises `GuardedReadRefreshUnavailable`, rather than returning empty data or clearing auth. This is a deliberate parity and availability limitation: V2 normally attempts refresh. The Home and block-body states preserve a distinct cause and render the existing truthful V2 `qolip.home.load_failed` text; unlike V2's retry surface, no retry or sign-in guidance/control is wired. An isolated 401 alone does not prove that the session expired. A test verifies that an actual new login and new Home owner read the same block afresh after a rejected locations future. An old owner's rejected future remains cached and is not retried in place. A real recovery flow, appropriate truthful user guidance and independently reviewed route remain open.

An earlier uncommitted attempt to propagate a witness through the shared credential refresh was discarded after independent review reproduced changed-scope, mid-upsert and iOS storage races, including new metadata/chunk writes after invalidation. Checking only before and after multi-await account publication was not safe. The current guarded observer cannot enter that path; an independently requested legacy refresh may still carry out its own existing writes after the observer is revoked, and is neither canceled nor represented as guarded work.

## Source comparison and open items

V2 `qolip_home_screen_models_resplit_part_01.dart:90-205` supplies the shell, search, block tabs, lazy bodies and retry; `_QolipHomeScreenState_methods_01.dart:46-107` supplies the initial read and saved order. The candidate omits menu/profile/dock, create, tab reorder, lifecycle refresh, cell tap/long-press, attach, movement, printing, scanner, Chat, checkout/return and every write. Neither pull-to-refresh nor retry is connected; for ordinary load errors the source's `AppRetryState` text still says to try again, but its retry button is intentionally absent. For refresh-unavailable errors this candidate instead displays the existing source `home.load_failed` text, which does not explain the session condition. Both are incomplete, non-releasable error states, not parity. A test-token mode, role route and full shell still need independently reviewed real dependencies.

The original checkout ledger's older-future/loaded-selection race is documented in `port/qolipchi`'s status file. Displayed or retained selection is not authority to dispatch stale return/bulk actions; all such actions remain held, and unknown write outcomes require authoritative settlement, not just a witness check.

No phone, simulator, native build, real backend, real credential, Flutter/Dart command, SQLite retry, push or merge was used. Native grid layout, scrolling, accessibility, focus and full iOS/Android behaviour still require real-phone checks. The source role's broad text and surface gates remain open; no text exception is accepted here.
