## Durable assignment hold prototype (not connected)
- `assignmentWriteHold.ts` is default-off and has no production storage or guard-evaluator implementation, no import by the existing commands and no startup storage access. It requires an injected strict synchronous evaluator and in-memory opaque scope snapshot, checks that snapshot before and after the guard, and accepts only a synchronous string owner ID of the expected shape. It specifies an atomic durable acquire/read/owner-conditional-release interface, reads its marker back before issuing a lease, serializes a single attempted `beforeSend`, and can automatically release only a reservation known not to have sent. An attempted request remains blocked even if a caller observes 400 or apparent success; there is no automatic refresh-based clear or implemented resolution UI.
- Tests simulate an atomic store shared by instances and a fresh runtime, including pre-send crash, uncertain write/read/delete acknowledgments, mismatched owner, concurrent release/send and account changes. They do not prove real SQLite durability, cross-process atomicity, OS/native dispatch timing, CSPRNG owner uniqueness, actual backend settlement, or crash recovery. A global marker can block unrelated accounts and lacks operation details for reconciliation; its privacy and user-facing resolution are unresolved. Plain `appPreferences` get/set is not an atomic store, no persistent marker has been written, and this prototype must not be connected to a route until independently reviewed and verified on devices.
