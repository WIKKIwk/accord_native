## Experiment
- `src/homashyo/rawSplitJournalPrototype.ts` is an unconnected, pure TypeScript experiment. No application source imports it; it has no real storage adapter, endpoint, retry, UI, printer code or switch enabling production work. The non-configurable `rawSplitWriteDispatchAllowed()` remains `false`.
- One versioned value per exact `(serverId, ownerRef)` tuple holds a fenced owner, revision, at most one active command and completed tombstones. Tuple JSON encoding prevents colon-delimited key collisions. A command retains exact request JSON and an embedded matching request ID.
- The candidate transitions are `prepared` → `uncertain` → `completed` → acknowledged tombstone. `uncertain` is intended to be durably recorded before any hypothetical send. Only a matching, externally authoritative terminal outcome can be recorded, and only the exact observed response at the current revision can be acknowledged. No transition resolves “not found,” retries, deletes or prints.
- All updates compare scope, owner generation/token and revision inside the assumed atomic updater. An old acknowledgment cannot erase a new command; used request IDs remain blocked. Invalid/future state fails closed. A full journal blocks further commands without pruning.
- Any update exception is conservatively indeterminate, including an updater rejection: it may have committed. A guarded status read can inspect the stored state, but a read is only a snapshot and can become stale. Session/legacy guards are sampled before, inside and after an updater; they cannot make an external owner transition or legacy writer exclusion atomic. The negative interleaving test demonstrates this limitation.
- A correct production solution is **not** obtained by changing the false policy flag, by treating mock tests as native durability evidence, by trusting a supplied boolean as exclusion, or by using the ordinary stock response/history snapshot as request identity.
