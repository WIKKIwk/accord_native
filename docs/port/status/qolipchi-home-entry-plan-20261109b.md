# Plan: make Qolipchi read-only Home testable

This is a proposed integration plan, not an implemented route or a claim of role parity. Candidate branch `port/qolipchi-home-readonly-20261109b` is based on `bffbcc0`; its reviewed Home checkpoints are `38f1d13` and `5701254`. No app route, navigation target, shared auth/notification or login redirect has been changed. The saved-order preference read may initialize native Expo SQLite KV schema; the role does not write the saved order itself.

## Current evidence

- `src/shared/appRoutes.ts:657-680` selects Qolip Home early for role `qolipchi` with `qolip.manage`, but also has a later capability-only Qolip fallback for other roles. The route/capability table already names `/qolip` and `qolip.manage` at lines 112 and 274-276. `homeTargets` at 708-720 has no Qolip platform entry.
- `src/app/index.tsx:23-36` restores/bootstrap-refreshes the session, asks `homeTarget`, and otherwise shows the existing V2 fallback. Returning an active Qolip session to `/` after adding a Qolip target would immediately redirect it back into Qolip; a bare `router.replace('/')` is not a sign-in or exit flow.
- `QolipSettledHomeSession` reads only the already-active in-memory session after transition/version checks, then captures once. The boundary enforces the exact original witness, `qolipchi`, `qolip.manage` and a real token. A cold or invalidated shell does not restore, recapture or revive itself.
- V2 `qolip_home_screen_models_resplit_part_01.dart:90-125` shows a drawer/menu, profile action and Home dock. The candidate only implements the search field, block tabs, passive grid/scrolling and the source retry button. `QolipReadOnlyHome.tsx:23-66` keeps other actions absent.
- Existing `WorkerSecurityProvider` includes PIN/biometric lifecycle and exposes an `onLogout` callback on lock/error surfaces. It cannot safely be supplied a fake callback. Existing `ProfileScreen` exposes edit, camera and upload behavior (`ProfileScreen.tsx:56-78,115-166`); its shared profile fetch is not opted into the new per-hop witness guard (`profileApi.ts:9-24`). It is not a ready-made read-only escape path.
- Existing `auth.logout` (`auth.ts:310-348`) can unregister a push token, contact the backend, remove a saved account and clear session data. These are real side effects, not a neutral navigation callback. The current scope keeps those actions held; using them from Qolip requires its own source/permission and concurrency review. The separate login 307/308 redirect question remains unresolved.
- Existing startup `bootstrapSession` (`src/shared/loginLogic.ts:31-50`) races profile refresh against two seconds; that refresh can finish after a role mount and change scope. A route cannot assume all startup profile work is settled merely because Index rendered. The original witness must invalidate the mounted screen on a later change; it must not be silently recaptured.

## Proposed staged integration, after review and authorization

1. Factor the existing Home content to accept the `session` and original boundary already returned by one role-local settled-entry owner. Reuse that exact boundary for Home, security/exit callbacks and deep-link checks; do not capture a second witness inside a nested shell. While login/scope transition is active, wait without mounting data. If the witness becomes invalid, remove old content immediately and require an explicit fresh entry after the transition; never make a stale owner revive after rollback.
2. Add thin platform-specific Expo Router entries, for example `src/app/ios-qolip/index.tsx` and `src/app/android-qolip/index.tsx`, pointing to the same role-owned gate/content. Check platform, active in-memory session, exact role, `qolip.manage`, non-demo token and the original boundary on direct entry as well as normal app startup. A cold deep link must return to the normal app bootstrap only when doing so cannot create a redirect loop, then create a new owner after a real session is established. Verify that existing root Stack auto-registration behaves as expected; do not assume it from static inspection alone.
3. Add a single Qolip platform mapping in `homeTarget`, **only** when the effective role is `qolipchi` and the capability check passes. Preserve existing behavior for every other role, including a non-Qolip role whose capability-only fallback currently resolves to `/qolip` but whose `homeTarget` is null. Do not rewrite `homeRoute`, global capability tables or the other roles. Tests must cover role/capability priority and direct deep links separately.
4. Bind only real read-only controls already implemented: search, existing block tab selection, grid scrolling/display, and user-triggered retry of a settled failed block or location GET. Preserve 401 as a visible failed read and never start automatic authentication. Keep create/reorder, cell taps/selection, placement/move, scanner, printing, Chat, profile editing, camera/upload, notification and all return/write actions hidden or disconnected; do not render controls with no-op callbacks.
5. Resolve the escape/re-authentication blocker **before** exposing a route. A reviewed source-backed, user-initiated profile/disconnect control could call the existing real logout workflow only after verifying the original witness, handling concurrent session changes, its push/server/local-storage effects and its actual success/failure. Reuse source labels and confirmation semantics, not a fabricated screen. Only navigate to `/` when the intended session is truly cleared and no replacement login/transition would be overwritten; then the existing `AppEntry` can accept a user login and the route must create a fresh owner. If logout/account switching remains held or cannot be verified, keep the route closed: the current retry button and OS navigation do not solve persistent 401 or provide a reliable sign-in path.
6. Integrate `WorkerSecurityProvider` only with that real reviewed logout/escape handler. Test PIN/biometric lock, load errors, background/foreground and session replacement without weakening other roles. Do not alter shared security, auth, login redirect or notification code as a shortcut.

## Required checks before a phone-test route

- Original-witness and route tests: missing session/capability, wrong role/platform, non-Qolip capability fallback, demo token, cold deep link, delayed startup profile response, same-account ABA, failed login rollback, account/scope change, stale callbacks and remount after explicit recovery. Assert no old-account data or GET after invalidation and no automatic witness renewal.
- Retry tests: initial/redirect/401 GET, old/new location futures, search-generation overlap, duplicate taps, timeout with an already-dispatched read, independently initiated legacy refresh, repeated 401 with no authentication, and a real user login followed by a fresh owner. Verify no write/retry/placement/scanner/printing/Chat control is reachable.
- Logout/recovery tests if separately allowed: duplicate confirmation, stale witness, failure, account switch or login while logout is pending, saved-account and push/server behavior, PIN cleanup, and navigation only after verified current-session outcome. No backend, credentials or device should be used for these tests.
- Rerun full Node tests, both platform typechecks, uncached lint, ledger/drift and role text/surface audits; report baseline failures and unimplemented V2 behavior. Independently review the exact final diff before route exposure. On actual phones, verify layout, retry button size/hit testing, scrolling, accessibility, app lock, logout/re-login and both platforms; no simulator/device has been used yet.
