# Admin UI contract (partial)

Source: V2 `f11910bb2c8c7081ce26770e69811b03fd0739ed`. This is an incremental contract for Admin home, activity, factory locations, additional settings, and parts of the drawer and dock only. Other screens, sheets, dialogs and create overlay still need complete contracts and V2/V4 audits; this file does not establish role completion or authorize a placeholder screen.

## AdminHomeScreen

V2: `lib/src/features/admin/presentation/admin_home_screen.dart:20`. `AdminShell` is in `widgets/admin_shell.dart`; `AdminStore` is in `features/admin/state/admin_store.dart`. The same home component is reused under the role/capability routing for Admin, sales manager and brigader. Use the existing native shared drawer, dock, cards and FAB/menu facilities where they can preserve the behavior below; do not duplicate a ready component.

- Title: sales manager uses the literal V2 `userRoleLabel` `Sotuv manageri`, brigader uses `Brigader`, all other profiles use localized getter `adminRoleName`. The selected drawer destination is the session's home route. The dock's active tab is home.
- The screen listens to `RefreshHub`; when a new version has topic `admin`, reload. After its first frame, it starts `AdminStore.bootstrapSummary()` only when the profile has `party.supplier.read`. Pull-to-refresh invokes the same gated reload, including for short content. On leaving an opened child route and returning, reload. Prevent duplicate route openings until the prior navigation and reload finish.
- If summary permission is absent, do not request the summary and display the capability-filtered action list. For sales managers hide the create-item, create-user, users and production-map-test candidates even if their routes are otherwise open; sales action cards omit their leading icon. Others show each candidate's icon. Candidate order, exact localized keys and route targets are represented in `src/admin/adminHomeModel.ts` directly from `_adminHomeActions`.
- With summary permission, before the initial load show the loading indicator while `loadingSummary && !loadedSummary`; show the retry state if `summaryError != null && !loadedSummary`. Retry invokes reload. Otherwise show, in this order, only routes `AppRouter.canOpenRoute` permits: factory map (`adminFactoryMapNavTitle`), quick orders (`adminQuickOrdersTitle`), open order (`adminOpenOrderTitle`), work map (`adminWorkMapNavTitle`). Cards display the title and an empty value, with no user-count cards. A later refresh error does not hide already loaded content.
- Each visible card opens its named route and refreshes after return. If a destination is not yet implemented, record it as an Open item rather than inventing a destination. Route capability checks must use the verified shared V2 guard rather than a new approximation. The `adminHomeModel` reuses V4 `canOpenRoute`. Forty relevant f119 route paths and capability sets match the shared guard for an Admin actor in the source-derived route inventory; role-specific conditions still need full end-to-end audit.
- The source has no direct haptic call in this screen. Exact back behavior, drawer destination details, dock primary FAB overlay dismissal and every destination's screen contract remain in the separate shell/overlay audit. The partial platform views use the shared list/card and receive their real shell, session-scoped store and route-return bridge as props; they are not routed or marked complete. Activity and any other unimplemented or unsafe destination must not be exposed via a fake route.

## Additional settings

V2: `admin_additional_settings_screen.dart`, `widgets/admin_app_update_settings_card.dart`, `widgets/admin_lamination_settings_card.dart`, and `widgets/admin_qolip_start_settings_card.dart`. Reuse one shared screen for Admin, Brigader and Rezka Master. The route guard allows Admin with `admin.access`, Brigader with `brigader.access`, and Rezka Master with `rezka.master.access`. Admin and Brigader see every card; Rezka Master uses the existing operator drawer and dock with no active tab or primary FAB, and sees only the two Paddon switches. Admin/Brigader use the existing Admin drawer and settings dock tab. Other roles see the V2 `productionErrorMessage('forbidden')` state if the component is opened directly. The selected route is `adminAdditionalSettings`; the Admin shell title is `productionText('paddon.management.settings.title')`, primary FAB hidden, with a refresh action disabled while Paddon save is in progress.

On entry read Paddon settings. Show the common loading indicator until the read completes and the common retry state on failure. Only after that read succeeds, Admin/Brigader cards begin their own independent settings reads; each displays its own busy indicator, load failure and retry, with switches disabled while busy, failed or not loaded. The order is mandatory app update (`appUpdateMandatorySettingTitle`, `appUpdateMandatorySettingBody`), Paddon free movement (`paddon.management.free_movement.title`, `.description`), Paddon worker visibility (`paddon.management.worker_visibility.title`, `.description`), lamination WIP label then film label (`lamination.settings.wip_label`, `.film_label`, `.label_description`), and automatic mold confirmation (`qolip.start.settings.title`, `.description`). Unloaded values are false for app update/Paddon/qolip and true for both lamination switches, but remain disabled until their read succeeds.

The owning shell must choose the leading control from the actual route stack: V2 uses a back action when the route can pop and is not first, potentially delegating to the native iOS back button; otherwise it uses the drawer menu. Its accessibility tooltip comes from Flutter `MaterialLocalizations`, not a hard-coded translation. The native screen accepts a shell-provided `navigation` object (`menu` or `back`, localized label and callback) or null to leave native iOS back in charge, plus the existing role dock as `footer`. The screen has not been wired into that shell yet.

Enabling Paddon free movement requires a confirmation using `paddon.management.free_movement.confirm`, `.description`, `no`, and `yes`; disabling does not. After confirmation and before sending, recheck the active session identity, the captured session read scope and role/capability. Paddon saves update only the submitted field and wait for the server-acknowledged result. On failure show `paddon.management.settings.failed` and reread Paddon settings; on success show `settingsSaved`. The other cards likewise wait for the server, show their exact `appUpdateSettingsSaveFailed`, `lamination.settings.save_failed` or `qolip.start.settings.save_failed` message on failure, and reread because a timeout may have saved server-side. Their read failure messages are `appUpdateSettingsLoadFailed`, `lamination.settings.load_failed` and `qolip.start.settings.load_failed`; use `retry`. Drop asynchronous results when session identity or scope changes. Do not expose a mutation before its account and permission checks, and do not fake a route for an unavailable shell.

## Factory locations

V2: `admin_factory_locations_screen.dart` and its `widgets_part_01`, `widgets_part_02` and `models_part_03`. On mount or pull-to-refresh, load locations and the existing apparatus catalog concurrently with limit 10,000; loading shows the common indicator and errors use `factory.states_load_failed` in the common retry state. Sort the apparatus catalog with IDs beginning `apparatus:default:` first by `sortOrder`, then custom equipment by lowercase name. The role shell uses `adminFactoryStatesNavTitle`, selects factory locations in the drawer and Home in the dock. Use the actual V2 route/capability allowlist, not an Admin-role-only check: its f119 test permits a Customer with `factory.location.manage`. The app-bar add icon and list button use `factory.state_create`; both and each row action are disabled while saving.

Each location row opens the editor on tap. It shows name, selectable ID, `factory.apparatus_state` when it has members or `factory.ordinary_state` otherwise, an additional `factory.inactive` badge when inactive, and member display labels resolved through the canonical apparatus catalog. The row menu offers `factory.edit_equipment`, `factory.rename`, and `factory.deactivate` or `action.activate` according to current status. Empty list uses `factory.no_states`.

The create/editor dialog uses `factory.state_create` or `factory.state_edit`, a `factory.state_name` field, `factory.attach_title`, selected equipment chips, and `action.save` / `action.cancel`. Editing makes the name read-only and shows `factory.state_id_note`; renaming happens in its own dialog with `factory.state_name_edit`. A missing name displays `factory.enter_state_name` and does not close. The equipment picker is a safe-area bottom sheet at 78% height, with `factory.state_search`, `factory.default_equipment` and `factory.custom_equipment` sections, `factory.no_equipment` on no matches, and a button labelled `factory.continue_without_selection` or `factory.selected_count`. Cancel preserves the previous selection; confirmation preserves the set's insertion order. Chips display selected IDs present in the catalog, but unseen selected IDs remain in the selection.

Create calls the existing create API with trimmed name and selected IDs. Editing only replaces equipment when the selected ID set differs, ignoring ordering; after create/edit upsert and sort locations by lowercase name. Rename skips empty or unchanged names, updates the name and resorts. Activation calls update and keeps row order. API exceptions display their message; other save, rename and activation failures use `factory.state_save_failed`, `factory.state_update_failed` and `factory.state_status_failed`. `factoryLocationEditorModel.ts` records the pure rules. The shared native editor content and platform picker contents are implemented but not yet hosted in a real dialog/sheet or wired to the controller. The reusable sheet's current full heights differ from V2's 78%; preserve cancel semantics on back, swipe and outside dismissal, and do not write until the original guarded editor ticket is revalidated. Partial platform screen and rename content are now implemented with an injected controller and shell callbacks; their real dialog hosts, safe async session integration, actual role shell and routing are still open. The rename content returns the trimmed name with its original ticket and silently leaves an empty name in the dialog; the controller handles the unchanged-name no-op. The header create action stays available during the initial load or error, unless a save is in progress; a forbidden state is additionally disabled for account safety. No route is exposed.

## Admin activity

V2: `lib/src/features/admin/presentation/admin_activity_screen.dart`. After the first frame, bootstrap activity and load the existing `NotificationHiddenStore`; listen to `RefreshHub` and refresh only on a new version for topic `admin`. Remove the listener on dispose. Back pops if possible, otherwise clears the stack and opens `adminHome`. The top-bar title is `adminActivityTitle`, with a clear-all icon and no subtitle; the Admin dock selects activity.

Security hold: do not expose this screen or connect hidden-store loading/clearing until the shared account-switch race is resolved. An old async `load` or `hideAll` can cross a reset into a different server with the same role/ref.

The clear-all icon always opens the shared confirmation dialog with `clearTitle`, `clearAllNotificationsPrompt`, `no` and `yes`. Only an affirmative result calls the existing hidden store with *all current activity IDs*, including IDs already hidden, for the active profile. The screen lists records not in that profile's hidden IDs in their original order. A first load shows the loading indicator only when no visible rows exist; the first failed load shows the shared retry state under the same condition. A loaded empty list uses `adminNoActivity`; later refresh errors retain existing rows. The list supports pull-to-refresh.

Each row uses the existing Admin summary card/list treatment, no chevron: supplier name is the title, created label the value, and the subtitle is `activity.sent` with the sent quantity to zero fixed decimal places and UOM. If accepted quantity is positive, wrap that with `activity.accepted` and the accepted quantity, also to zero fixed decimal places. Status icons in enum order are schedule filled, schedule outlined, done-all, check, close and remove, in a 36-point circle with an 18-point icon. `adminActivityModel.ts` captures these decisions; neither platform view nor its lifecycle, confirmation, hidden-store wiring or navigation is implemented yet.

## Admin dock and default create overlay (partial)

V2: `widgets/admin_dock.dart` and `widgets/admin_create_hub_sheet_models_part_02.dart`. Ordered dock candidates are home, user, primary create and activity, each filtered by `AppRouter.canOpenRoute`; an explicitly supplied primary action keeps create available. The primary action has no selected tab. It is visible only when `showPrimaryFab` is true, the profile overlay does not obscure it, a primary destination exists and its menu is closed. Selecting it opens the create overlay. Selecting the active non-primary tab does nothing, except selecting Home while the current route is not the session home replaces the root with the home route. Other dock selections replace the root.

The default create overlay lists permitted actions in this order: create user (`adminCreateUserTitle`), create item (`adminCreateItemTitle`), progress QR scan (`adminQrScanTitle`), quick orders (`adminQuickOrdersTitle`), open order (`adminOpenOrderTitle`). Visible actions animate with reverse stagger order. `src/admin/adminDockModel.ts` captures these default candidates and dock decisions. Custom action overrides, the overlay's open/close and back behavior, platform animation and the actual shared FAB/dock integration remain open. Do not enable Chat unread live from this shell until the verified no-redirect, no-cookie transport exists.
