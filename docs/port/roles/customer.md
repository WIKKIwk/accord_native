# Customer UI contract

Source: V2 `f11910bb2c8c7081ce26770e69811b03fd0739ed`. This is a behavior contract, not evidence of a completed port. Customer uses the existing profile, chat, shared role drawer, shared notification stores and the Supplier-owned `NotificationDetailScreen`. `CustomerStore`, Customer API methods, response rules, session, notification and both platform view bindings are in `src/customer/`; shared notification detail remains an integration dependency.

## Shell, navigation and common states

- `CustomerNavigationDrawer` (`customer_navigation_drawer.dart`) has, in order, `homeNavTitle` (Uy), `notificationsShortTitle` (Bildirish), and `profileTitle` (Profil), plus the shared logout action. Selecting the current item only closes the drawer; the others replace the current root route. Profile is the existing shared profile screen.
- `CustomerDock` (`customer_dock.dart`) has home, notifications and the shared `Chat` destination in that order. Home and notifications use `AppRootNavigation`: a matching route is popped to, an absent route is pushed, and choosing the active destination does nothing. Rapid requests within a frame coalesce to the last target after keyboard focus is dismissed. Drawer choices replace only the current route. A notification unread dot is shown except while notifications is active. The shared chat unread dot comes from `ChatStore.unreadCountListenable`. On status and delivery details the Customer dock has no selected Customer tab. The shared chat screen is not re-created.
- Shared retry state uses `serverDisconnectedRetry` (Server uzilgan. Qayta urining.) and `retry` (Qayta urinish). Loading uses the shared loading indicator. No additional empty, error, permission or offline text is specified for these Customer surfaces.
- Customer home and notifications listen for a new `RefreshHub` version with topic `customer` and refresh after the current frame. All relevant data is session-scoped; account changes clear `CustomerStore`, delivery runtime state, hidden/unread notification state, and `cache_customer_notifications` in V2 `app_runtime_reset.dart`.
- No Customer-specific FAB, search field, bottom sheet, back guard or explicit haptic is present in these source files. Platform controls and existing shared components may draw natively without changing labels, surface kind or action order.

## CustomerHomeScreen

Source: `customer_home_screen.dart`, `customer_home_screen_widgets_part_01.dart`, `customer_home_screen_widgets_part_02.dart`. Enter from the Customer home route. `CustomerStore.bootstrap()` loads summary and the pending, confirmed and rejected status lists concurrently; it avoids a second load while loading and does not reload an already loaded store unless forced. `refresh()` sets loading and clears error, waits for all four requests, then updates snapshots and the history merged by ID in pending/confirmed/rejected order and sorted by descending created label. On initial failure, show retry. A later failure retains prior data and error without replacing the displayed content. Pull to refresh is available even for short content.

- Title `customerRoleName` (Haridor). The first card has rows `pendingLabel` (Kutilmoqda), `confirmedStatus` (Tasdiqlangan), `rejectedLabel` (Rad etilgan), each with its corresponding count and a tap target to the matching `CustomerStatusDetailScreen`. Always refresh on returning from status detail.
- Next card title `recentShipmentsTitle` (So‘nggi jo‘natmalar). With no history show `noShipments` (Jo‘natma yo‘q); otherwise show all merged history records in order, each with item name and item code capped at one line with a trailing ellipsis, and sent quantity fixed to zero decimal places plus unit. Open the corresponding Customer delivery detail. Refresh on return when the detail reports a change.

## CustomerStatusDetailScreen

Source: `customer_status_detail_screen.dart`; argument is `pending`, `confirmed` or `rejected`. Title is respectively `pendingLabel`, `confirmedStatus` or `rejectedLabel`. Bootstrap the store. Initial loading and failure follow the common states; a loaded empty list shows `noRecordsYet` (Bu ro‘yxatda hozircha yozuv yo‘q.). A nonempty list supports pull to refresh and displays item name, created label, sent quantity fixed to zero decimals and unit, then the note only if its trimmed value is nonempty. The name and note have no explicit line cap, unlike Home previews. Tap opens delivery detail and refreshes on a changed result. Back returns to the prior screen; the bottom dock remains available with no Customer tab selected.

## CustomerNotificationsScreen

Source: `customer_notifications_screen.dart` and its widget parts. Enter through notifications, drawer or dock. Bootstrap the Customer store; load hidden IDs, unread IDs and the `cache_customer_notifications` JSON list. Until the store is loaded, cached records can be shown. Filter hidden records and put highlighted unread records before other records while retaining order within each group. If loading with no stored/cached items show loading; on initial error with no items show retry inside the refreshable list; empty shows `noRecordsYet`. The list supports pull to refresh, including short content.

- Title `notificationsTitle` (Bildirishnomalar). Nonempty section title `shipmentsFlowTitle` (Jo‘natmalar oqimi). A record displays status icon, item name and code, note if nonempty or the exact fallback `${sentQty.toStringAsFixed(0)} ${uom} jo‘natildi`, and created label. The item name has no explicit line cap; code is capped at one line and note/fallback at two lines with a trailing ellipsis. Unread records are highlighted. Tapping marks that ID seen, removes its highlight and opens its Customer delivery detail.
- The clear action is always present. Open a confirm dialog with title `clearTitle` (Tozalash), body `clearAllNotificationsPrompt` (Hamma bildirishnomalarni tozalaysizmi?), `no` (Yo‘q) then `yes` (Ha). Cancel or outside/back dismissal changes nothing; confirmation hides all current history IDs for the profile, marks them seen and clears highlights.
- Synchronizing from the store first marks hidden IDs seen, retains only current history IDs in the unread store, computes highlights from the remaining unread IDs and writes all history records to the JSON cache. Store changes schedule a sync after the frame; refresh also syncs. Cache/reset behavior must follow V2 and not leak a prior account's records.

## CustomerDeliveryDetailScreen

Source: `customer_delivery_detail_screen.dart`, `customer_delivery_detail_screen_widgets_part_01.dart`, `customer_delivery_detail_screen__CustomerDeliveryDetailScreenState_methods_01.dart`. Argument is the delivery note ID. Fetch `customerDeliveryDetail` on entry; loading and initial errors use the common indicator and retry. Pull to refresh refetches. Title `detailsTitle` (Batafsil), back is a normal maybe-pop, and the Customer dock has no selected Customer tab.

- Section `shipmentInfoTitle` (Jo‘natma ma’lumoti): `customerLabel` (Haridor) = supplier name; `itemLabel` (Mahsulot) = `itemCode • itemName`; `pendingStatus` (Jarayonda) = sent quantity fixed to 2 decimals and unit; if accepted quantity > 0, `acceptedFromQtyPrefix` (Qabul) = accepted quantity fixed to 2 decimals and unit; `statusLabel` (Status) = accepted `approvedLabel` (Tasdiqlandi), partial `partiallyCompleted` (Qisman yakunlangan), rejected `rejectedStatusLabel` (Rad etildi), otherwise `pendingLabel` (Kutilmoqda).
- If note is nonempty after trim, show `noteTitle` (Izoh) and the original note. For accepted, partial or rejected records show `commentsTitle` (Izohlar) and `openDiscussionAction` (Muhokamani ochish), opening shared NotificationDetail with `customer_delivery_result:${deliveryNoteID.trim()}`; refresh when it returns.
- If any response permission is true, show `responseTitle` (Javob) and permitted buttons in this order: `approveAction` (Tasdiqlayman), `partialAcceptAction` (Qisman qabul qilish), `rejectAction` (Rad etaman), `reportIssueAction` (Muammo bildirish). While a response is being submitted all response buttons are disabled and the approve label is `sending` (Yuborilmoqda...).
- Approve opens a confirm dialog: `confirmTitle` (Tasdiqlash), `confirmQuestion` (Haqiqatan ham tasdiqlaysizmi?), `no` then `yes`. Confirm sends `approve: true`, mode `accept_all`.
- Reject, partial and claim open a dialog, respectively `rejectTitle` (Rad etish), `partialAcceptTitle` (Qisman qabul), `reportIssueTitle` (Muammo bildirish). In partial and claim show a numeric return-quantity input first: partial label `returningQtyLabel` (Qaytarilayotgan miqdor), claim label `returnedQtyLabel` (Qaytarilgan miqdor), hint sent quantity fixed to two decimals and unit, with the unit suffix. Reject has no quantity entry. Then show `reasonLabel` (Sabab), selectable/toggleable reasons in order `rejectReasonDefective` (Yaroqsiz), `rejectReasonWrongItem` (Noto‘g‘ri mahsulot), `rejectReasonQtyMismatch` (Miqdor noto‘g‘ri); then `extraCommentLabel` (Izoh) with `optionalReasonHint` (Sabab (ixtiyoriy)); then `no` and `yes`.
- The yes action is enabled only if a reason is selected or trimmed comment has at least three Unicode code points, and, where quantity is required, it parses after comma-to-dot replacement and is > 0. For partial it must be strictly less than sent quantity; for claim it may equal it. Reject sends all sent quantity with `approve: false`, mode `reject_all`; partial sends `accepted_qty = sent - returned` and mode `accept_partial`; claim sends mode `claim_after_accept` and returned quantity. Preserve reason and trimmed comment as V2 does.
- Successful response updates the delivery runtime transition, emits a Customer refresh and pops with changed=true. Failure stays on the detail and shows a short snackbar `responseSendFailed(error)` (Javob yuborilmadi: {error}). Back/outside dismissal cancels dialogs; V2 adds no separate saving back guard.

## Shared NotificationDetailScreen

Source: `features/shared/presentation/notification_detail_screen*`. Supplier owns this separately. Customer opens it only via the delivery-result event ID above. It marks the event seen, loads its record/comments, permits a comment under the V2 record/status rules, handles refresh/account change and returns to delivery detail. A direct Customer receipt ID beginning `MAT-DN-` redirects to Customer delivery detail. Its exact strings, dialogs and Snackbar behaviors are part of the Supplier-owned shared surface and still require integration and audit here.
