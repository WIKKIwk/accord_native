# Rezka role UI contract

Source: V2 `f11910bb2c8c7081ce26770e69811b03fd0739ed`. This is a working contract, not a claim that any surface is complete.

## Reachability

`AppSession.homeRoute` selects `apparatusQueue` for a `rezka_master` with `rezka.master.access`. `AppRouter.canOpenRoute` allows only `apparatusQueue`, `apparatusDailyWork`, `apparatusWorkInstructions`, `apparatusPaddons`, `apparatusPaddonDetail`, `adminWorkerSettings`, and `adminAdditionalSettings` for that role, in addition to common account/profile/chat routes. `rezkaSplit` is not in that allowlist. The separate `rezkaSplit` route belongs to sessions that pass its `rezka.split.manage` capability guard. Do not add it to the master drawer. V2 references: `app_router_AppRouter_resplit_class_AppRouter_resplit2_static_methods_02.dart:28–37` and `_routeCapabilities.dart:87`.

## Master workers and apparatus

V2: `AdminWorkerSettingsScreen`, `admin_worker_settings_screen.dart:62–96`, `_methods_01.dart:22–185`, `_methods_02.dart:145–220`, `_widgets_part_06.dart`, `widgets/admin_apparatus_scope_picker.dart`. Hook/controller: `src/rezka/useRezkaWorkerSettings.ts`, `rezkaWorkerController.ts`. The platform views and real assignment handler are connected through the guarded master-only shell; device testing and authoritative unknown-write reconciliation remain open.

- Master sees the operator shell, `worker.title`, no admin tabs or creation actions. The existing Aparatchi drawer and dock are reused; dock has `activeTab: null` and `showPrimaryFab: false`.
- Initial load and pull refresh start `rezkaMasterWorkers()` and `adminApparatus(limit: 500)` together. Show a loading indicator until both complete, `worker.load_failed` if either fails, `worker.empty` for an empty team, otherwise preserve the server's worker order. One card expands at a time.
- A card heading displays worker name, localized level (unknown level falls back to `3 - darajali`) and nonempty phone. Expanded details in order: `worker.worker_details` with name; `worker.name_label`, `worker.level`, `worker.phone_label` (or `worker.not_entered`), `worker.id`; `scope.operator_title` apparatus selection. Master cannot edit name, level, deactivate, create, or manage groups.
- Picker is a dismissible, draggable bottom sheet with title `scope.operator_title`, subtitle worker name, description `rezka_master.rezka_apparatus_required`, then `scope.allowed` and the loaded apparatus list as checkboxes. Initial selection includes only assigned IDs present in that list. Empty selection disables `scope.save_action`; saving prevents another save, selection changes and the sheet’s close button, and uses `action.saving`. The modal itself uses Flutter defaults and can still be dismissed by back, swipe or barrier; completion may then update the underlying list.
- Save normalizes selected IDs by trimming, removing duplicates and sorting. A canonical set equal to the saved assignment does not issue a write and shows `scope.already_assigned` with sorted names. Otherwise PUT includes worker ID, the selected list, and the unmodified previous list. A success closes the sheet, shows `scope.saved` for five seconds and reloads. `rezka_worker_has_open_run` leaves the sheet open and shows a live error in the sheet, including worker and blocked apparatus names when supplied. `rezka_assignment_changed` and master `worker_not_found` close, show `rezka_master.rezka_assignment_changed` and reload; `rezka_apparatus_required` and other errors use the source's notices.
- Scoped data and mutation attempts belong to the exact active session and captured capability/apparatus scope. No 401 retry may send with a different session or scope. A sent request whose result becomes uncertain must not be silently retried or shown as success. Screen hookup still requires reliable invalidation when the same Session object is mutated in place.

## Assigned Paddon preparation

V2 `aparatchi_paddon_scope.dart`, `canonical_apparatus_groups.dart`, `aparatchi_navigation_drawer.dart` and `aparatchi_paddons_screen.dart` define this operator path; `rezkaMaster` is an apparatus operator. `rezkaPaddonScope.ts`, `rezkaPaddonApparatusController.ts` and `useRezkaPaddonApparatus.ts` prepare its read-only scope logic but are not connected to either shell and do not expose a destination.

- The drawer skips its apparatus read only when the assigned list is empty; otherwise its reader uses the existing `adminApparatus(limit: 10000)` with the shell's original master witness and a pre-send/401 guard. Failure, an empty catalog or no matching assignment yields no Paddon drawer entries. A React effect replay shares one read; a changed session/scope, reset or unmount retires the old read and cannot display a late result.
- V2 first keeps exactly `active` machines, groups by trimmed/lowercased operation and uses the `cut` group. It sorts by catalog order and then lowercase name, and matches against a set of individually trimmed assigned IDs using exact, case-sensitive membership. Ties compare equal in V2; its sort does not specify tie order. V4 does not mutate the catalog.
- The Paddon screen auto-selects a sole assigned cutting machine on an unscoped entry; with zero or multiple options, it asks for a selection. A supplied route ID and name are trimmed, and an empty name is resolved by exact ID when available. V2's route-to-display resolution is not itself an authorization check, so the pure helper must not be used to authorize an arbitrary incoming ID.
- For a selected machine V2 filters the returned Paddons again by exact apparatus ID, preserves server order, and totals displayed Paddon count and `itemCount` WIP. The unscoped multi-machine state does not load a Paddon list.
- The existing shared `adminPaddons` reader accepts an optional synchronous guard while retaining the legacy two-argument `authorizedFetch` call when no guard is supplied. `readRezkaPaddons` supplies the original master witness, route capability and exact assigned ID at first send and any 401 retry, and rechecks after successful or failed body decoding before returning data or an error. Blank or unassigned IDs fail closed. A caller must still verify the machine is an active cutter against the guarded catalog before using this unconnected adapter.
- `useRezkaPaddonList` and `RezkaPaddonReadOnly.ios.tsx` / `.android.tsx` now prepare unconnected native read-only content. The controller reuses the guarded limit-10000 catalog and list adapter, verifies the selected ID is among active assigned cutters, supports V2's initial loading, error/retry and pull refresh, and shows summary metrics, empty text, list counts and the optional rewinding subtitle using the existing localization catalog. It never loads an unscoped list and cannot send the second read after suspension/unmount. Refresh generations prevent an older response from replacing newer content. The invalid supplied-ID behavior deliberately fails closed; V2 instead lets the backend decide. The hook also reloads if only the supplied name prop changes, whereas V2 reacts to an ID or loader change.
- Still open: Paddon selector and row navigation, detail screen, real drawer destination, the native operator dock and its primary actions, scoped navigation, create/delete/transfer/printing and safe unknown-write reconciliation. The prepared unscoped machine labels and list rows are intentionally noninteractive, with no fake buttons; the V2 empty-state text mentions creation while that action is held. Do not expose this partial content as a full screen. The shared HTTP implementation does not call its send guard before each redirect hop, and an already dispatched native request cannot be recalled; those redirect/dispatch limits require review before exposure. No Paddon route or write was activated by this preparation. Source-derived Node assertions and mocked native component renders are not an executed V2 oracle or phone validation.

## Master work instructions

V2 `features/aparatchi/presentation/aparatchi_work_instructions_screen.dart:14–378`. This shared operator surface is reachable by Rezka masters; its V4 implementation is scoped to this role and changes no Worker/Preparation files. `RezkaWorkInstructions.ios.tsx` and `.android.tsx` use `useRezkaWorkInstructions` and the shell's original witness. The drawer entry `worker.instructions` follows daily work and any assigned-Paddon entries, before Profile. iOS uses its native stack; Android keeps the existing role shell, drawer and bottom bar.

- On each screen mount, read the existing guarded `adminApparatus(limit: 300)` once, with no query, automatic refresh, error message or retry action. This is a read, never an assignment write. Show centered loading until it settles. A failure, empty response or no assigned match all show `worker.guide.no_machine.title` and `.body`, as V2 does.
- Trim assigned IDs, drop blanks and duplicates case-insensitively, retaining the first spelling. Then match apparatus IDs exactly against that retained list. Preserve the returned apparatus order, not assignment order; do not case-fold membership, filter by family or load beyond the source's limit.
- Header title and subtitle are `worker.instructions` and `worker.guide.subtitle`, present during loading/empty too. With assigned rows, show `worker.guide.intro`, then `worker.guide.open_order` with five numbered steps and `worker.guide.states_actions` with four. Each apparatus card follows in response order, with its name and kind, then before-start, pause, complete and partial sections. Numbers restart at 1 per section, using `${index + 1}. ${text}` exactly.
- A trimmed/lowercased `print` operation uses four start, three pause, three completion and three partial steps. Flexographic technology takes the flexo kind label; otherwise null color count uses the generic machine label, and any supplied count, including zero, is interpolated. `laminate`/`glue` use the three-step lamination groups, with glue retaining the apparatus name as its kind label. `cut` uses the cutting groups, all three steps. Other operations use generic machine groups with only two pause steps. All words come from the existing four-language production catalog; there is no new translation table.
- Witness/scope loss or runtime reset redacts and retires the read. A suspended valid instance retains its one read for React effect replay and only publishes its result after resume; an unmounted instance is disposed. A 401 retry must pass the original witness's shared send guard.
- `test/aparatchi_work_instructions_screen_test.dart` content assertions were read and retained in source-derived Node checks. Its legacy human-name assignment/demo setup was not executed or presented as a selected-source API recording. No new Dart oracle, native build, backend or device test was run.
- Still partial: V2 uses `AparatchiDock(activeTab: null)` with the default primary action menu. The existing V4 non-queue shell has no such reviewed menu, and iOS NativeTabs still selects Home for nested instructions. Those shared-shell gaps are recorded, not replaced with new scanner/Paddon destinations. Native title/subtitle wrapping, back, light/dark, large text and Urdu layout require device validation.

## Split, item picker and scanner

V2 `rezka_split_screen.dart`, `_methods_01.dart`, `_methods_02.dart`, `_declarations_part_01.dart`. Source and split APIs: `src/rezka/rezkaSplitApi.ts`; pure barcode, draft and quantity rules: `rezkaSplitLogic.ts`. Both native platform screens, the item picker and full-screen scanner are exposed at the capability-guarded `/rezka-split` route, with the original captured session witness. A capability-only home can open the route; the master allowlist still denies it. Real source/item reads, form editing and camera scanning are connected, but there is no reviewed printer bridge, so the route explains this and blocks all split/print mutations. Scanner startup/release recovery, authoritative uncertain-outcome recovery, cross-screen write locking and the reused snackbar offset remain open.

- Screen: `Rezka`, subtitle `Mahsulotni bo‘lish`, Source QR field, scan action, `QR ni tekshirish`, printer selector. A successful source read replaces drafts with two empty outputs seeded with source unit (or `kg`) and warehouse; it shows source name/code/quantity/location. Add output, remove only while more than two. Per output show product selector for QR outputs or `Atxot: QR chiqarilmaydi`, quantity, UOM, location, reason, then overall reason and expandable Printer fields (Driver URL, Printer, Mode). Submit is `Bo‘lish va QR chiqarish`; loading and submission disable their respective buttons.
- Item picker is a bottom sheet, search `ERPNext item qidirish`, 220 ms debounce, `gscaleItemsPage(query, limit: 30)` and `Mahsulot topilmadi` empty state. Selecting an item sets code, name, UOM (default `kg`) and nonempty warehouse. The scanner is a full-screen dialog, `QR scan`, QR and Data Matrix, with `Scanner bu qurilmada ishlamaydi` where unsupported; cancellation has no effect.
- Scanner implementation: `RezkaSplitScanner.ios.tsx` uses native SwiftUI dialog chrome; `.android.tsx` reuses the shared native role header. `RezkaScannerPreview` reuses `CameraSurface` and `useCameraSurfacePermission`, with the back camera, no torch and no new controls. `RezkaScannerOwner` accepts the first trimmed nonempty raw value, falling back to display data only when raw is null/absent. It closes the dialog before passing that value through the existing `RezkaSplitController.scan` parser and source read. Back/cancel has no field or request effect. A result carries the dialog and owner lifetime through its promise continuation, so a newer dialog, account/scope change, focus change, app suspension or unmount cannot revive an old accepted result. App suspension preserves an open dialog and pauses the camera; resume rechecks permission before using a grant. Runtime reset retires the owner permanently.
- Scanner error content follows the vendored V2 `third_party/mobile_scanner/lib/src/mobile_scanner.dart:323–349` and `enums/mobile_scanner_error_code.dart`: black placeholder, white error icon, `Camera permission denied.` or `An unexpected error occurred.`, plus the native detail when present. These plugin-default words remain untranslated, as in V2. The Uzbek unsupported-platform message is not used for denied permission on the two supported mobile platforms. Expo's untyped mount error cannot reproduce the V2 no-camera classification yet. V2's global camera coordinator, startup retry/deadlines and detection-error recovery remain open, along with native camera, permission, light/dark and dismissal validation. Scanner assertions are source-derived mocked Node tests, not a newly executed V2 scanner oracle or hardware test.
- V2 local printing prepares first, prints QR-enabled outputs with nonempty EPC, and only then checks prepared count and confirms. The unconnected V4 controller deliberately checks count, output flags and required EPCs before physical print, rejects native `ok: false`, and confirms only after each real print succeeds. Remote/Wi-Fi calls direct split. Never confirm after a failed local print. Do not report an uncertain backend mutation as failed or repeat it automatically. Existing shared picker extraction needs a safe transient consumer and supported USB/Bluetooth/Wi-Fi transports; GoDEX is excluded by project decision. No fake printer or successful print is allowed.
- Output validation requires item on QR outputs, positive quantity and location; scrap can inherit source item. Total within 0.0001 is accepted; a remainder opens `Miqdor yetmayapti` with `Unutibman`, `Brak mahsulot`, `Bekor qilish`, and adds the selected new draft before requiring another submit. Scrap goes to `brak - ombori - A`, no QR and reason `Atxot / brak mahsulot`. Excess shows the V2 snackbar. Server total mismatch can add remaining output or show a mismatch message as in `_methods_02.dart`.
- Exact messages, loading, back/sheet dismissal, printer errors and user-visible text still need platform-by-platform audit. No simulator or phone validation has been performed.
